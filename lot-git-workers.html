LOT Git Workers: machines the tree cannot reach can help prove

Normally a LOT tree runs its sessions only on its own host (or in its own Slurm job). Git workers hand some obligations to another machine, and the two sides cannot reach each other over the network: all they share is one git repository, and each work order is a branch in it (not a GitHub issue or PR). The tree stays the master and decides what goes out; a proof that comes back still has to pass the tree's gate.

2 · How the collaboration is set up

A work order is a git branch. No GitHub issues, no pull requests.

The master (whoever runs the tree) and the collaborator (whoever runs a worker) share nothing but one git repository, here a private GitHub repo. No SSH, no VPN, no shared disk, no open port on either machine. The collaborator only needs push access to that repo: the master invites them as a GitHub collaborator.

What holds the work orders?
Branches in one git repository. One order = one branch, lot-orders/<tree>/<obligation>-<n>. The branch's files are the ticket: the Lean module to prove, the lib it builds on, and .lot-order/ORDER.json with the frozen statement and the rules.
Are GitHub Issues or PRs used?
No. No issues, pull requests, comments, labels, Actions or GitHub API calls. Both sides only run git ls-remote, git fetch and git push. GitHub is just where the repository lives; any git server both sides can push to would do. (gh is used only to log in and to download the setup kit.)
Then what is ISSUE.md?
A file inside the order branch: the obligation's task written out in words for the worker's agent. It is not a GitHub issue.
How is "taking a ticket" exclusive?
The worker takes an order by creating the branch lot-claims/…/<order> with a push that succeeds only if the branch does not exist yet. Two workers racing for one order: one push wins, the other is rejected and moves on.

Master · once
  1. Create the orders repo with a main branch (a README is enough; it must not be empty, or the first order could never be deleted).
  2. Put the worker kit on main: README, setup.sh, worker.sh, the trusted checker byte for byte (with its sha256), and a release with the LOT and hmz sources.
  3. Invite the collaborator.
  4. Start (or revive) the tree with git workers on:
ltree run --name putnam-1970-b6-pair ... \
  --param git_workers=hold \
  --param git_remote=https://github.com/<org>/<orders-repo> \
  --param git_worker_model=claude/deepseek-v4.1-flash:max \
  --param git_worker_min_depth=1 \
  --param git_worker_wait=300 --param git_worker_lease=6h \
  --param git_worker_poll=30
Collaborator · once, about 1 h
  1. Accept the invitation; gh auth login.
  2. Clone the orders repo and run bash setup.sh: it downloads LOT and hmz from the release, checks their SHA256 and the checker's, and builds the same Lean, Mathlib and checker tools at the same absolute paths the checker names.
  3. Set up an agent CLI (Claude Code pointed at DeepSeek here, or any model).
  4. Start the worker before the master puts orders out (an order waits only 5 minutes):
WORKER_ID=ziyang-brev-flash bash worker.sh
# which runs:
python3 -I lean_option_tree/docker/git-worker.py \
  --remote https://github.com/<org>/<orders-repo> \
  --tree putnam-1970-b6-pair --id "$WORKER_ID" \
  --model claude/deepseek-v4.1-flash:max \
  --split-depth 1 --race --poll 30 --heartbeat 300

How an order is put out

Every git_worker_poll the tree looks for obligations it may hand out: open, at depth ≥ git_worker_min_depth, all dependencies proved, not marked split-further, never sent before, and not already worked on by the tree for more than 5 minutes. The deepest go first, up to git_worker_orders at a time. For each, it commits a snapshot in its own git and pushes it as a branch. Everything else in the exchange is a branch too:

BranchPushed byWhat is in it
lot-orders/<tree>/<obl>-<n>masterThe lib at that moment, the obligation's module with by sorry, .lot-order/ORDER.json and .lot-order/ISSUE.md (the task in words).
lot-claims/<tree>/<obl>-<n>workerCreated to take the order: creating a branch only succeeds for the first pusher, so exactly one worker gets it. Then one heartbeat commit every --heartbeat seconds.
lot-results/<tree>/<obl>-<n>workerThe obligation's files, .lot-order/RESULT.json (proved or gave-up) and the agent's NOTES.md.
statusmasterOptional STATUS.md, rewritten every 2 minutes: who holds each node, each order's state, recent events. What the collaborator reads to follow along.
mainmasterThe worker kit. Orders never touch it.

The master deletes an order's three branches when it ends (landed, untaken, withdrawn, stale, lease over, or the tree ends), so the repo only ever shows what is live. A worker sees its order disappear within one --poll and stops.

Not every order lands: the other endings

untaken
No worker takes it within 5 minutes. The order is deleted and the obligation is the tree's; the tree resumes its paused sessions with their conversations kept.
Example: o002, o003; x0009–x0011 resumed at minute 32.7
withdrawn
The obligation no longer needs a proof (the tree proved its parent, or it was superseded). The tree deletes all three branches; the worker notices within one --poll and stops, pushing nothing.
Example: o009 (the tree proved o004 directly), o015 (o002 proved directly)
stale
The claim has had no heartbeat for 30 minutes. The tree takes the worker for gone and takes the obligation back.
gave-up / lease over
The worker pushes gave-up, or the lease (12 h by default) runs out. Either way the obligation is the tree's.
tree ends
Proved, deadline or cancelled: every order still out is withdrawn.

Hold-mode rules: no work done twice, none dropped

  • An obligation goes out at most once. If it comes back unproved, it stays with the tree for good.
  • For 5 minutes after it goes out (git_worker_wait) it belongs to the workers only. The tree pauses its own PROVE / DEC on it, starts no new ones, leaves it out of the preemption plan, and the gate refuses a lot offer of it from any other session (409).
  • An obligation the tree has already worked on for more than 5 minutes is never put out.
  • Only obligations at depth ≥ git_worker_min_depth, with all dependencies proved and not marked split-further, go out; the deepest first.

    5 · What if the worker had 2 slots

    putnam_1970_b6 again, with a worker that holds 2 orders at once

    Here a slot is one order the worker holds. In the real run the worker held one order at a time, so while it was on o001 every other order went untaken. Within an order, the worker still runs its own race and split (prove lane, split, sub-lemmas) no matter how many slots it has. Today git-worker.py takes one order per process, so 2 slots means two worker processes with different --id on the same machine.
