An improvement tree: how many agent sessions build one solver together

LOT proves a frozen Lean statement by splitting it into lemmas that many sessions prove in parallel. LOT-I v2 runs the same kind of collaboration on tasks with no formal statement — here, heuristic solvers from TCSExam that are scored on hidden instances. This page walks through one real tree, the AHC041 “Christmas tree cutting” task, run on DeepSeek V4.1 Flash (1017) for every role. For the proof side, see how a LOT proof tree proved Dijkstra's universal optimality, session by session.

    The tree: who worked where

    The same tree as a structure. Under the task are its variants (architectures) and the rejected proposals; under each variant its slots; on each slot the IMPROVE sessions that worked there, the idea each was given, and every submission with its gate decision. Each variant names the ARCH session that proposed it and the AUD session that reviewed it. Each session is one line of the tree: IMPROVE sessions under the slot they worked on (their idea and result: the commits they landed, or their promote wins/losses), ARCH and AUD sessions under the variant or proposal they wrote or reviewed. A slot with many sessions lists the ones that landed something or are live and sums up the rest. Drag the time to watch it grow.

    How to read the tree

    variant
    One complete architecture of the solver: a glue file (the main program that calls the parts) plus a set of slots, each one part with a fixed interface (for example construct, search, lns). v0 is the starter code as a single slot v0.app. Variants compete: whichever one scores best is the champion, and that is what gets delivered. Only a few variants stay alive at once; when a new one is added, the weakest non-champion variant is retired and its sessions are stopped.
    variant v1 · from p002 · slots v1.glue, v1.construct, v1.search …
    proposal
    A plan for a new variant plus its code skeleton: how to split the solver into slots, the exact interface of each slot, simple but correct stub implementations, and why this shape can beat the current champion. A proposal becomes a variant only if the audit accepts it; otherwise it stays in the tree as a rejected leaf, with the reason.
    proposal p001 · rejected — plan targets a stale champion
    arch session
    The architect. It reads the champion and the scoreboard and writes a proposal. Along with the plan it commits the skeleton (glue plus stub slots, which must build and run), so IMPROVE sessions can start on the slots as soon as it is approved.
    aud session
    The auditor. A separate session that reviews one proposal and either accepts or rejects it, reading the code at the proposal's commit. It checks that the slots are real, separable parts with precise interfaces, that the stubs are honest (not hiding the real work in the glue), that the time budget is not hard-coded, and that the plan explains how it can beat the champion. The ARCH session cannot approve its own plan.
    improve session
    The worker. It is assigned one slot and one idea (or "free choice"), and may change only that slot's files. Each change it submits goes through the gates: screen (does it build and run within the limits), then promote (a paired comparison against the current code on the same instances; it must win more instances than it loses). A change that passes is landed: it is committed, and the tree line shows the commit and the gain. Failures show as screen ✗ or promote ✗ wins/losses.

    So the work splits two ways: ARCH and AUD decide what shape the solver has (new variants), and IMPROVE sessions make each shape better, one slot at a time. Sessions in different slots and different variants run in parallel.

    怎么读这棵树（中文）

    variant（变体）
    求解器的一种完整架构：一个 glue 文件（主程序，负责调用各部分）加上若干 slot，每个 slot 是接口固定的一个部件（比如 construct、search、lns）。 v0 是初始代码，只有一个 slot v0.app。变体之间互相竞争，得分最高的是 champion，最终交付的就是它。同时存活的变体数有上限；新变体加入时，最弱的非 champion 变体会被淘汰，上面的 session 也会停掉。
    proposal（提案）
    新变体的方案加代码骨架：怎么拆成 slot、每个 slot 的精确接口、简单但正确的占位实现，以及为什么这种结构能超过当前 champion。 只有审核通过才变成变体；被拒的提案作为叶子留在树上，并写明理由。
    arch session（架构师）
    读 champion 和得分表，写出 proposal，同时提交骨架代码（glue 加占位 slot，要求能编译、能运行）。审核一通过，improve session 就能直接开始做各个 slot。
    aud session（审核员）
    一个独立的 session，读提案对应 commit 的代码，判断接受还是拒绝。检查 slot 是否真能独立拆开、接口是否精确， 占位实现是否诚实（没有把真正的工作藏在 glue 里），时间预算有没有写死，方案有没有说清楚怎么超过 champion。arch 不能批准自己的提案。
    improve session（干活的）
    分配到一个 slot 和一个 idea（或者 "free choice"，自由发挥），只能改这个 slot 的文件。每次提交都要过两道门： screen（能否编译，能否在限制内跑完），然后 promote（在同一批实例上和当前代码成对比较，赢的实例数要多于输的）。 通过就是 landed：提交成 commit，树上显示 commit 和提升幅度；没通过显示 screen ✗ 或 promote ✗ 胜/负。

    分工就是两条线：arch 和 aud 决定求解器的结构（产生新变体）， improve 在每种结构里一个 slot 一个 slot 地把它做好。不同 slot、不同变体上的 session 并行运行。

    1. Why a proof tree does not fit an optimization task

    In LOT, a split closes its parent only when every child is proved (an AND), and the root closes once. A first version of LOT-I copied that onto solver tasks: a split into components, each with its own test, and the root “solved” at its first acceptance. On five TCSExam solver tasks every root was closed by a direct implementation within an hour and no decomposition ever counted: components passed their own tests without the whole getting better, the glue had to wait for all siblings, and once the root closed the tree was just sessions editing one file.

    LOT-I v2 keeps LOT's discipline — frozen interfaces, a trusted checker that alone decides, sessions on their own git branches, a controller that alone writes the integration branch, independent reviews — but replaces “prove once” by improve monotonically, measured in context.

    2. Who does what

    IMPROVE sessions

    Each owns one slot of one variant and one idea from that slot's list. It edits only the slot's files, measures with loti eval, and loti submits small gains. It sees a per-instance scoreboard (including the gap to the best known value) and the notes of earlier sessions.

    ARCH sessions

    Propose a new variant: a glue plus slots, each slot with a stub, a frozen interface spec, an optional unit test and 3–6 ideas. The root never closes, so this can happen at any time.

    AUD sessions

    Review a proposed variant before it opens: are the slots real, separable parts? are the stubs honest, the tests meaningful, the time budget not hard-coded?

    Controller (trusted)

    The only process that writes the integration branches. A candidate = the variant's current best with only the submitting slot's files replaced; it is judged through the task's own scorer, never in the session's sandbox.

    Evaluation queue (own CPUs)

    screen5 instances: no new failures, not clearly worse
    promote16–30 instances, paired with the incumbent instance by instance: mean gain, more wins than losses, sign test
    hold-outinstances no session ever sees + a few at a long limit: a new champion must not regress, else it is rolled back
    marginon 2-second tasks, a run over 85% of the limit counts as a failure

    Variants & slots

    Each variant (architecture) has its own best commit v/<id>. An accepted slot change lands at once — no slot waits for its siblings.

    Champion

    The best variant's best commit, on lib: the deliverable at every moment. It moves only through the promote gate and the hold-out check.

    Sandbox

    Each session runs in a private root: its desk, its home, the tree's repository read-only, the public instances read-only at /app/instances. The hidden instances, the hold-out set and the judge do not exist inside; network only to the model API.

    3. A worked example: Christmas tree cutting

    The task (AtCoder AHC041, as a TCSExam solver task): a planar graph of 1000 vertices with weights; assign every vertex a level 0–10 so that each vertex above level 0 has a neighbour one level lower, and maximize Σ (level+1)·weight. One core, 2 seconds per instance; the final score is the Kimi-K3-relative score on 45 hidden instances (50 = Kimi K3's own result).

    The tree after 5 hours

    • 48 sessions: 35 IMPROVE, 9 ARCH, 4 AUD — three IMPROVE and one ARCH running at a time on one CPU core, evaluation on a second core.
    • 59 gate decisions: screen 28 passed / 3 rejected; promote 8 accepted / 20 rejected (97 evaluations in total).
    • 3 live variants: v0 (the starter, one slot = the whole solver), v1 and v2 (proposed by ARCH sessions, approved by AUD); 2 further proposals rejected.

    3.2 The official score exposed a blind spot — and the gates were fixed

    The tree's g kept rising, but the hidden-set score did not: at 06:32 the champion scored 40.0 with 5 of 45 hidden instances at 0. The solver ran to 1.7–2.0 s of its 2-second limit; on the public instances it happened to finish, on the judge it was sometimes killed. Two changes followed, without restarting the work: (1) the finish margin — any run over 85% of the limit is a failure in every gate, so the risky champion now shows failures and any safe solver beats it (the 07:14 step, “+1.999”, is a safe solver replacing it); (2) the scoreboard shows each instance's gap to the best known value in %, because the official score compares with solvers within ~1% of it, where g has no resolution left.

      5. What the run taught the workflow

      • Gate on the judge's terms. A proxy that passes solvers at 99% of the time limit is wrong on another machine: short-limit tasks need a finish margin.
      • Show the gap that the final score sees. Normalized scores saturate near the best known value; sessions need the per-instance gap in %.
      • Never starve the slow stages. With 15–30-minute evaluations, a priority queue let screens starve promotes and promotes starve champion checks; all stages of a submission now share one FIFO priority and champion checks go first.
      • Decomposition comes after a strong baseline. In this tree the useful architectures were proposed only once a single-slot champion existed to decompose; the stubs are the champion, so a variant starts at full strength and every slot gain is a real gain.
