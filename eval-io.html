What every evaluation reads, and why one cluster complained

Our LOT-I runs judge candidate solvers thousands of times per tree, each time in a fresh Slurm job. On our old Brev cluster this is harmless. On the new one the same scripts made the login node's disk serve so much network traffic that the cloud provider flagged the whole cluster. This page lists what each evaluation reads, why it is a separate job, and what differs between the two machines.

Short version. Every evaluation starts cold: it copies the submission, rebuilds it from source with the C++ compiler, starts Python (and for some tasks a Java VM) and reads its instances. All of that lived under /home. On the old cluster /home is served by a dedicated storage server; on the new cluster it sits on the login node's own disk, so every compute node read the toolchain and the data through the login node, tens of thousands of times.

Part 1

What a TCSExam evaluation reads

What one evaluation of a candidate solver does, which files it reads, and why it reads them again every time, following the judging rules of the TCSExam paper.

1.1 What one evaluation does

An evaluation scores one candidate solver on a few instances (inside a tree) or on the whole hidden set (final judging). It reproduces the official TCSExam judge without Docker:

new Slurm job (or job step), 1 pinned core per instance, its own memory limit
 ├─ private root: user + mount + network namespace, /app = a fresh copy of the submission
 ├─ start the judge          python3.12  judge_native.py
 ├─ rebuild the submission   bash /app/build.sh   → g++ (compiler, headers, libstdc++, binutils)
 ├─ run the solver           solver INSTANCE OUTPUT LIMIT   (reads the instance file)
 └─ verify + score           task checker (Python; a Java VM for hs/ds; cvc5 for sygus; drat-trim for qbf)

Nothing of this is kept between evaluations: the next one starts from scratch.

Scale: one five-task batch on the old cluster (three repetitions, 15 trees of 12 hours) ran about 340,000 evaluation jobs (Slurm array tasks). Without cache hits, 100–300 MB per job would be terabytes. How much the compute nodes' page cache absorbs we have not measured yet; with short jobs under tight memory limits, cached pages are easily reclaimed between jobs.

1.3 Why the same files are read again on every evaluation

Our evaluation reproduces the paper's final solver judging (TCSExam, Appendix D.2 and the task instructions) as closely as we can without Docker. Each of its rules turns into reads that repeat:

What repeatsThe rule in the paper's judging it comes from
A full rebuild from source in every evaluation unit: the compiler, a few hundred headers, the assembler and the linker are loaded again each time. Final judging is one unit per instance, so the same program is compiled once per instance (85 times for job-shop).“The frozen program is rebuilt and evaluated under the task's separate execution limits.” The official worker runs the frozen checker “in a fresh Docker worker”, and the task instructions say the verifier rebuilds /app from what was left there. Submissions also hard-code /app, so every unit gets its own fresh /app and runs build.sh in it.
One job (or job step) per instance, each a new process tree that starts Python and the task's checker from scratch.“Per-instance tasks limit each instance separately.” “We use up to ten isolated sandboxes concurrently … Each instance retains the specified time, CPU, and memory limits.” The instructions specify one core and a fixed memory reservation per instance. A separate job with one pinned core and its own memory limit is how we give each instance exactly that. (The six shared-pool tasks are judged as one group, as the paper requires.)
The verifier starts again for every instance; for hitting set and dominating set that is one Java VM per instance.The paper judges with each task's own frozen checker, unchanged. For these two tasks the checker is the official PACE Java verifier, called once per instance.
The same procedure inside the trees (screen / promote / hold-out), only with shorter limits and fewer instances.So that a candidate's in-tree score measures what the final judging will measure: same rebuild, same isolation, same checker.

On top of these rules, two properties of a network file system make every one of those starts reach the file server:

  • Every open is checked with the server. NFS guarantees close-to-open consistency: when a process opens a file it asks the server whether the file changed, even when the contents are already in the node's memory.
  • Failed lookups cost a round trip too. The compiler tries several include directories for each header; the shell searches every PATH directory for each command (including directories under /home); Python and the compiler resolve /home, /home/… component by component. Each miss is a request to the server.

And the jobs are short and run under tight memory limits, so file pages one job brought into memory are easily reclaimed before the next job on that node needs them (likely; not measured).

Measured with strace on one real in-tree evaluation (cluster editing, one instance, 3.8 s, on the old cluster): about 8,000 file-system operations on network storage, about 1,000 of them for files that do not exist, 277 files opened, about 110 MB read — Python 30 MB, the C++ compiler cc1plus 39 MB, assembler, linker and shared libraries 30 MB, headers 4 MB. The instance itself was a few KB.

1.4 Why every evaluation is a new job

The obvious alternative is to give each round (or each tree) one big node and run all its evaluations there. We do not, for two reasons:

  • Queuing wastes time. Evaluation load is bursty: after an architecture change ten sessions submit at once, each promote check is 30 instances × up to a minute. On one fixed node those bursts queue behind each other, and a tree pauses while its gate waits for a result. Separate jobs spread over every free core in the cluster, so a burst finishes in about the time of one evaluation.
  • Queuing makes the data wrong. Solver scores depend on how much work fits into a wall-clock limit. If evaluations share an oversubscribed node, they compete for cores, memory bandwidth and caches, and the same solver scores differently depending on what else is running. The official judge gives every instance one pinned core with its own memory limit; one job (or job step) per instance reproduces exactly that, so in-tree scores are comparable to the final hidden score and to each other.

The price is the cold start of 1.2 and 1.3: every job reloads the same toolchain and data. That is fine when the files come from a storage server close to the compute nodes, and not fine when they come from a login node.

On the new cluster compute nodes cannot submit jobs, so there the evaluations of a tree run as Slurm job steps inside the tree's multi-node allocation (one step per instance, same pinning and limits), and final judging runs as Slurm arrays from the login node. Both start cold in the same way.

2.2 The 20 minutes before the alert

The scripts were written on the old cluster, where /home comes from a real file server, and moved unchanged to the new cluster. There the same path belongs to the login node: an ordinary VM whose disk and network card suddenly served compilers, runtimes and instances to every evaluation on 19 nodes. The provider reported about 8 million packets within 10 minutes around 15:39 UTC on 26 November (23:39 Beijing time). That is exactly when several of our things were scheduled to start at the same moment.

2.3 Why so many packets, not just bytes

8 million packets in 10 minutes is about 13,000 per second. NFS does not only move file contents: every file a process opens is first looked up and its attributes checked, each a small request and reply. One C++ build opens a few hundred header files; a few hundred builds starting together turn into a flood of small metadata packets on top of the bulk reads (Python, compiler, JDK, instances).

So the alert was not the steady load of a running experiment but a burst we scheduled ourselves: final judging of ten trees, 13 sessions and five new trees were all triggered by the same event, the end of repetitions 1 and 2.

2.4 What we change

  1. Read once per node. Stage the toolchain and the instances of the tasks in use onto each compute node's local disk the first time a job lands there (with a lock so it happens once); evaluations, builds and sessions then read locally.
  2. Never from the login node. The master copy moves to the shared data store; /home on a login node is only for the user.
  3. Measure before scaling up. Run one tree for an hour and read the per-mount byte counters on the compute nodes (/proc/self/mountstats) before restarting the full experiments.
  4. Quieter login node. One watcher polling every few minutes instead of dozens polling every minute.
  5. Stagger the starts. Final judging, new sessions and the next repetition no longer fire on the same event: judging is released in small batches, sessions and trees start a few at a time with gaps between them.

每次测评读了什么，以及为什么一个集群被告警

LOT-I 的每棵树要对候选程序做成千上万次测评，每次都在一个新的 Slurm 作业里进行。在老集群上这没有问题；同样的脚本放到新集群，却让登录节点的磁盘产生了大量网络流量，整个集群被云服务商告警。本页说明每次测评读了什么、为什么每次测评单独开一个作业，以及两台机器的区别。

简短版。每次测评都是冷启动：复制一份提交的代码，用 C++ 编译器从源码重新编译，启动 Python（有的题还要启动 Java 虚拟机），再读实例。这些东西都放在 /home 下。老集群的 /home 由一台专门的存储服务器提供；新集群的 /home 却在登录节点自己的磁盘上，于是每个计算节点都经由登录节点读编译器和数据，读了几万次。

第一部分

TCSExam 测评要读什么

一次候选程序的测评做了什么、读了哪些文件，以及按照 TCSExam 论文的评测规则，为什么每次都要重新读一遍。

1.1 一次测评做了什么

一次测评给一个候选程序打分：树内测评跑几个实例，最终评测跑整个隐藏集。它在不用 Docker 的情况下复现 TCSExam 官方评测：

新的 Slurm 作业（或作业步），每个实例独占 1 个绑定的核，有自己的内存上限
 ├─ 私有根目录：user + mount + network 命名空间，/app = 提交代码的一份新拷贝
 ├─ 启动评测脚本   python3.12  judge_native.py
 ├─ 重新编译       bash /app/build.sh   → g++（编译器、头文件、libstdc++、binutils）
 ├─ 运行程序       solver INSTANCE OUTPUT LIMIT（读实例文件）
 └─ 验证并打分     题目自带的 checker（Python；hs/ds 用 Java 虚拟机；sygus 用 cvc5；qbf 用 drat-trim）

两次测评之间什么都不保留，下一次又从头开始。

规模：老集群上一批 5 道题（跑 3 次，共 15 棵 12 小时的树）大约跑了 34 万个测评作业（Slurm 数组任务）。如果没有缓存命中，每个作业读 100–300 MB，总量就是 TB 级。计算节点的页缓存能挡住多少，我们还没有实测；作业很短、内存上限又紧，作业之间缓存的页很容易被回收。

1.3 为什么每次测评都要把同样的文件再读一遍

我们的测评在不用 Docker 的前提下，尽量照搬论文的最终评测流程（TCSExam 附录 D.2 和各题的任务说明）。论文评测的每一条规则，落到实现上都会变成重复的读取：

重复的事来自论文评测的哪条规则
每个测评单元都从源码完整重新编译：每次都重新加载编译器、几百个头文件、汇编器和链接器。最终评测是一个实例一个单元，所以同一个程序每个实例编译一遍（job-shop 是 85 遍）。“The frozen program is rebuilt and evaluated under the task's separate execution limits”（冻结的程序会被重新编译，再按题目单独规定的执行限制评测）。官方 worker 在“a fresh Docker worker”（一个全新的 Docker 容器）里运行冻结的 checker；任务说明也写明，评测器会用留在 /app 里的内容重新编译。提交的代码还会写死 /app 路径，所以每个单元都有自己全新的 /app，并在里面运行 build.sh。
每个实例一个作业（或作业步），每次都是新的进程，从头启动 Python 和题目的 checker。“Per-instance tasks limit each instance separately”（按实例计时的题目，每个实例单独限制）。“We use up to ten isolated sandboxes concurrently … Each instance retains the specified time, CPU, and memory limits”（最多同时用十个隔离的沙箱，每个实例都保有规定的时间、CPU 和内存限制）。任务说明规定每个实例一个核、固定的内存。单独一个作业、绑定一个核、有自己的内存上限，就是我们给每个实例提供这些条件的方式。（六道共享时间池的题按论文要求作为一组评测。）
每个实例都重新启动验证器；hitting set 和 dominating set 是每个实例启动一次 Java 虚拟机。论文用每道题自带的、冻结的 checker 原样评测。这两道题的 checker 是 PACE 官方的 Java 验证器，每个实例调用一次。
树内测评（screen / promote / hold-out）用同一套流程，只是时间更短、实例更少。这样候选程序在树内拿到的分数，衡量的就是最终评测会衡量的东西：同样的重新编译、同样的隔离、同样的 checker。

在这些规则之上，网络文件系统的两个特性，让每一次启动都会打到文件服务器上：

  • 每次打开文件都要和服务器确认。NFS 保证“打开-关闭一致性”：进程打开一个文件时，要先问服务器文件有没有变，即使内容已经缓存在本机内存里。
  • 找不到的文件也要走一次网络。编译器为每个头文件依次尝试好几个 include 目录；shell 执行每条命令前都要在 PATH 的每个目录里找一遍（包括 /home 下的目录）；Python 和编译器会把 /home、/home/… 逐级解析。每一次没找到，都是一次对服务器的请求。

此外，作业很短、内存上限又紧，一个作业读进内存的文件页，很容易在同一节点上的下一个作业用到之前就被回收（可能如此，尚未实测）。

在老集群上用 strace 跟踪了一次真实的树内测评（cluster editing，1 个实例，3.8 秒）：对网络盘约 8,000 次文件操作，其中约 1,000 次是查找不存在的文件；打开 277 个文件；读约 110 MB——Python 30 MB、C++ 编译器 cc1plus 39 MB、汇编器、链接器和共享库 30 MB、头文件 4 MB。实例本身只有几 KB。

1.4 为什么每次测评都开一个新作业

一个直接的替代方案是：每一轮（或每棵树）分配一个大节点，所有测评都在上面跑。我们没有这样做，原因有两个：

  • 排队浪费时间。测评的负载是突发的：一次架构变更之后，十个会话会同时提交测评，每次 promote 检查是 30 个实例、每个最多一分钟。固定在一个节点上，这些突发的测评就会互相排队，而树在等测评结果的时候是暂停的。分成单独的作业，就能分散到整个集群所有空闲的核上，一波突发测评大约只要一次测评的时间就跑完。
  • 排队让数据不准。求解程序的分数取决于在限定时间内能做多少计算。如果测评挤在一个超额分配的节点上，就会抢核、抢内存带宽、抢缓存，同一个程序的分数会随着旁边跑着什么而变化。官方评测给每个实例一个绑定的核和独立的内存上限；每个实例一个作业（或作业步）正好复现这一点，树内的分数才能和最终隐藏集分数、以及彼此之间相互比较。

代价就是 1.2、1.3 节说的冷启动：每个作业都要重新加载同一套工具链和数据。文件来自离计算节点很近的存储服务器时，这没有问题；来自登录节点时，就出问题了。

新集群的计算节点不能提交作业，所以在那里，一棵树的测评是在这棵树的多节点分配里用 Slurm 作业步来跑的（每个实例一个作业步，绑核和限制都一样），最终评测则从登录节点以 Slurm 数组提交。两种方式都同样是冷启动。

2.3 为什么是包多，而不只是字节多

10 分钟 800 万个包，大约每秒 1.3 万个。NFS 不只是传文件内容：进程每打开一个文件，都要先查路径、查属性，每次都是一来一回的小包。一次 C++ 编译要打开几百个头文件；几百个编译同时开始，就在大块读取（Python、编译器、JDK、实例）之外，又叠加了海量的小元数据包。

所以告警的不是实验平稳运行时的负载，而是我们自己安排出来的一次突发：十棵树的最终评测、13 个会话、5 棵新树，都被同一个事件——第 1、2 次运行结束——同时触发了。

2.4 我们怎么改

  1. 每个节点只读一次。作业第一次落到某个计算节点时，把工具链和本次实验用到的题目实例复制到该节点的本地盘（加锁，只复制一次）；之后的测评、编译和会话都读本地。
  2. 不再从登录节点读。主副本搬到共享数据存储；登录节点上的 /home 只留给人用。
  3. 先测量再放量。恢复完整实验之前，先跑一棵树一小时，读计算节点上每个挂载点的字节计数（/proc/self/mountstats）。
  4. 让登录节点安静下来。用一个每隔几分钟轮询一次的监控脚本，代替几十个每分钟轮询的脚本。
  5. 错开启动。最终评测、新会话和下一次运行不再由同一个事件同时触发：评测分小批放出，会话和树每次只启动几个，中间留出间隔。
